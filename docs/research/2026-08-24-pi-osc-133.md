# Do pi's OSC 133 prompt marks give a structured status channel?

Research for [andybarilla/jackdaw#17](https://github.com/andybarilla/jackdaw/issues/17). Date: 2026-08-24.

> **The ticket's question is answered and closed; one follow-on was cut short.** This session
> was stopped mid-investigation for a machine reboot (`/tmp`, a 31 GB tmpfs, hit 100% and was
> failing builds fleet-wide). The **OSC 133 verdict is complete** and the raw-evidence sections
> supporting it are finished — that is what #17 asked. What this study additionally *found* and
> could not finish is the follow-on lead: **Claude Code also has OSC 9;4 code**, read from the
> binary but never run. That is now
> [#18](https://github.com/andybarilla/jackdaw/issues/18), and
> [§8 Where this stops](#8-where-this-stops) is its brief. Raw logs and scripts survived the
> reboot at `~/.cache/jackdaw-r17/`.

**Question.** `pi` emits OSC 133 prompt marks — 52 in a single turn, spotted by
[#8](https://github.com/andybarilla/jackdaw/issues/8). Do they constitute the structured
channel [#2](https://github.com/andybarilla/jackdaw/issues/2) concluded `pi` does not have?

**Method.** Two kinds of evidence, held apart:

- **Primary source.** `pi` 0.84.1 ships as unminified JavaScript at
  `~/.local/lib/node_modules/@earendil-works/pi-coding-agent/dist/`, so every escape sequence it
  can emit is readable, along with the condition that emits it. Line numbers below are from that
  install. `claude` 2.1.231 and `codex` 0.147.0 are single-file bundles, scanned with `grep -a`.
- **Experiment.** A private tmux server (`tmux -L jackdaw-research-17`) on `apbfw16`; the live
  fleet socket was never contacted and no `send-keys` went outside it. Following #8's method:
  a **positive control first**, then two independent observers on every run — a **100 ms
  sampler** (`display -p` of `#{pane_pb_state}`/`#{pane_title}` plus `capture-pane`, every
  changed frame to disk) as ground truth, and **`pipe-pane`** writing the raw pre-render bytes
  through a stamper that logs `(timestamp, offset, length)` per chunk so any byte offset in the
  reassembled stream maps back to a wall clock. Escape sequences are matched against the
  **reassembled** file, not per chunk, so a mark straddling a read boundary is not lost.
  `pi` ran with `PI_CODING_AGENT_DIR` pointed at a scratch config dir; the user's real
  `~/.pi/agent/settings.json` was never modified.

**Versions.** tmux **3.7c** · `pi` **0.84.1** · `claude` **2.1.231** (the symlink on this
machine reads `versions/2.1.231`, not the 2.1.241 the ticket cited — reporting what was
observed) · `codex` **0.147.0**. `cursor` is **not installed** and was not tested.

---

## Verdict

**OSC 133 from `pi` is not a status channel and cannot become one. The lead is closed.**

It is a *render artifact*. `pi` wraps every rendered message block in `133;A … 133;B 133;C` for
its own scrollback navigation, and those bytes leak to the terminal only because the
non-alt-screen renderer writes its lines verbatim. Four findings each kill it independently:

1. **There is no `D`.** `pi` defines exactly three constants — `A`, `B`, `C`. Zero `133;D` in
   the source, zero on the wire in 460 KB of captured output. No command-end, no exit status,
   ever. (The instrument was controlled: `133;D;0` and `133;D;7` both reach `pipe-pane`
   verbatim on this tmux — §1.)
2. **`B` and `C` are byte-adjacent, always.** They are emitted as one concatenated string.
   Observed: **30 of 30** `133;B` immediately followed by `133;C`, **0** exceptions. A
   "command start" contiguous with "prompt end" spans no interval and times nothing.
3. **The marks are absent exactly when the agent is working hardest.** `AssistantMessageComponent.render()`
   returns early when `hasToolCalls` — so a tool-running turn is not marked. Observed: a
   two-tool turn produced 11 `B`/`C` against 19 for a no-tool turn of similar length.
4. **They vanish entirely in `pi`'s fullscreen mode**, which the user can toggle at runtime.
   `tuiMode: "fullscreen"` uses `TuiAltScreen`, which strips the marks before writing.
   Observed: **zero** OSC 133 in a whole fullscreen session.

**But the study found the channel the ticket was looking for, in the same place.**
`pi` emits **OSC 9;4 progress** — `9;4;3` (indeterminate) on `agent_start`, re-sent as a 1 Hz
keepalive, `9;4;0` on `agent_end` — driven by the session event bus, not the renderer. tmux
**3.7** parses it into **`#{pane_pb_state}`**, a first-class format, so it is readable with
`display -p` and pushable over `refresh-client -B` with **no `pipe-pane` and no scraping at
all**. Measured: `indeterminate` **22 ms** after submit, `hidden` at turn end, one clean
ON/OFF pair per turn including across tool calls.

It is **off by default** (`terminal.showTerminalProgress`, default `false` — which is why #8
saw none) and it **raises the substrate floor from tmux 3.2 to tmux 3.7**.

So: **`pi` is promotable out of the scraping fallback — but by OSC 9;4, not OSC 133, and only
if Jackdaw's adapter turns the setting on at launch.** #2's "adapters must contribute *launch
arguments*, not just observe" is exactly the mechanism this needs.

## 2. What `pi` actually marks, from its own source

```js
// dist/modes/interactive/components/user-message.js:4-6   (identical in assistant-message.js:4-6)
const OSC133_ZONE_START = "\x1b]133;A\x07";
const OSC133_ZONE_END   = "\x1b]133;B\x07";
const OSC133_ZONE_FINAL = "\x1b]133;C\x07";
```

The author's own names are `ZONE_START` / `ZONE_END` / `ZONE_FINAL`. Both components apply them
in `render()`, as a decoration of a *laid-out block of lines*:

```js
// user-message.js:41-47
render(width) {
    const lines = super.render(width);
    if (lines.length === 0) return lines;
    lines[0] = OSC133_ZONE_START + lines[0];
    lines[lines.length - 1] = OSC133_ZONE_END + OSC133_ZONE_FINAL + lines[lines.length - 1];
    return lines;
}
```

```js
// assistant-message.js:60-68
render(width) {
    const lines = super.render(width);
    if (this.hasToolCalls || lines.length === 0) return lines;   // <-- tool turns are unmarked
    lines[0] = OSC133_ZONE_START + lines[0];
    lines[lines.length - 1] = OSC133_ZONE_END + OSC133_ZONE_FINAL + lines[lines.length - 1];
    return lines;
}
```

Three things follow directly, before any experiment:

- **`A` marks a *user* message too.** The mark that OSC 133 nominally means "prompt start" fires
  when pi renders the block containing what the user just submitted — i.e. at the moment the
  agent starts working, the opposite of *awaiting input*.
- **`B` and `C` are one string.** `OSC133_ZONE_END + OSC133_ZONE_FINAL` are concatenated onto the
  same line with nothing between them.
- **`hasToolCalls` suppresses the whole thing.**

And the marks are `pi`'s *internal* convention, not an outward signal. `pi-tui` consumes them:

```js
// pi-tui/dist/tui-alt-screen.js:20-21
const OSC133_ZONE_PREFIX = /^(?:\x1b\]133;[ABC](?:\x07|\x1b\\))+/;
const OSC133_PROMPT_START = /^\x1b\]133;A(?:\x07|\x1b\\)/;

// tui-alt-screen.js:241-254 — scrollToPrompt(direction)
for (let row = scrollView.scrollTop + direction; ...; row += direction) {
    if (!OSC133_PROMPT_START.test(lines[row] ?? "")) continue;
    scrollView.scrollTo(row);
```

`133;A` is a **scroll anchor**. And both `tui-alt-screen.js` (lines 157, 848) and `layout.js`
(line 223) `.replace(OSC133_ZONE_PREFIX, "")` before compositing — they strip the marks. Only
`tui-main-screen.js`, the non-alt-screen renderer, contains no strip and therefore leaks them.

`grep` over the entire `pi-coding-agent` install: **`133;A` 9 hits, `133;B` 6, `133;C` 6,
`133;D` 0.** There is no `D` in the product.

### 2.1 The differential renderer explains the 2-vs-25 asymmetry

#8 saw 2 `133;A` against 25 `133;B` and 25 `133;C` in one turn and reasonably read it as
"52 marks per turn". The cause is `tui-main-screen.js`'s repaint diff (lines 260–286): it finds
`firstChanged`/`lastChanged` over the line array and rewrites only that range, verbatim. During
streaming, the **last** line of the assistant block changes on nearly every frame — and it
carries `B`+`C`. The **first** line stops changing early — and it carries `A`.

**The mark count is a function of the diff algorithm's changed-range, not of anything the agent
did.** That is the whole of what "52 marks per turn" measures.

### 3.2 Abort is handled; the source says why

`Esc` mid-turn → `hidden` inside 100 ms. From `interactive-mode.js`, every call site:

```js
case "agent_start":       ... this.ui.terminal.setProgress(true);    // :2492
case "agent_end":         ... this.ui.terminal.setProgress(false);   // :2648
case "compaction_start":  ... this.ui.terminal.setProgress(true);    // :2664
case "compaction_end":    ... this.ui.terminal.setProgress(false);   // :2678
stop() {                  ... this.ui.terminal.setProgress(false);   // :5369
```

all guarded by `this.settingsManager.getShowTerminalProgress()`. The emitter:

```js
// pi-tui/dist/terminal.js:9-11, 412-427
const TERMINAL_PROGRESS_KEEPALIVE_MS = 1000;
const TERMINAL_PROGRESS_ACTIVE_SEQUENCE = "\x1b]9;4;3\x07";
const TERMINAL_PROGRESS_CLEAR_SEQUENCE  = "\x1b]9;4;0\x07";

setProgress(active) {
    if (active) {
        process.stdout.write(TERMINAL_PROGRESS_ACTIVE_SEQUENCE);
        if (!this.progressInterval)
            this.progressInterval = setInterval(() => {
                process.stdout.write(TERMINAL_PROGRESS_ACTIVE_SEQUENCE);
            }, TERMINAL_PROGRESS_KEEPALIVE_MS);
    } else { ... write(TERMINAL_PROGRESS_CLEAR_SEQUENCE); }
}
```

`pi` only ever emits `9;4;3` and `9;4;0`. **It never uses `9;4;2` (error) or `9;4;1;N`
(determinate percentage).** The channel is one bit — *working* / *not working* — plus liveness.

### 3.3 The failure mode, and which direction it fails in

Emitter frozen mid-turn (`SIGSTOP` on the pane process) and `#{pane_pb_state}` sampled:

```
  pb before stop        : indeterminate
  pb  5s after SIGSTOP  : indeterminate
  pb 15s after SIGSTOP  : indeterminate
  pb 30s after SIGSTOP  : indeterminate     (still indeterminate minutes later)
```

tmux holds the last value indefinitely, exactly as #8 found for `pane_title`. So **`pane_pb_state`
needs the same per-pane staleness clock #8 already demanded** — a dead emitter and a long turn
are the same observation to a `-B` subscriber.

Two things soften it, and one of them is architectural:

- It fails **stuck-working**, never stuck-idle. #8's item 6 — "a false-idle is the failure that
  costs" — is the hazard this signal does not have. A supervisor over-waiting is recoverable;
  a supervisor handing new work to a busy agent is not.
- The **1 Hz keepalive makes liveness observable on the raw stream**. `pipe-pane` sees `9;4;3`
  every second while working; a gap > ~2 s means the emitter stopped. `refresh-client -B` cannot
  see this — it pushes on *change*, and a keepalive re-sends the same value. **The two reachability
  tiers differ in what they can prove**, and that is the reason to care which one Jackdaw builds.

## 4. Two controls that make the verdict specific

### 4.1 Default settings: no OSC 9;4 at all

A fresh `pi` with `terminal.showTerminalProgress` unset (its default), same prompt, same rig:

```
--- ctlA-default: alt=0 pb=hidden title=π - proj
    +1s … +12s   pb=hidden   (every second, throughout the turn)
    final pb=hidden alt=0 hist=19
    [ctlA-default] raw=296220B  OSC: {'8;;': 374, '133;B': 18, '133;C': 18, '133;A': 2, '0;π - proj': 1}
```

**Zero `9;4`. And `133;A: 2, B: 18, C: 18` — #8's numbers, reproduced.** The default-off gate is
why #8 saw the marks and not the channel. The relevant source line:

```js
// dist/core/settings-manager.js:796-797
getShowTerminalProgress() {
    return this.settings.terminal?.showTerminalProgress ?? false;
}
```

Set via `~/.pi/agent/settings.json` (`{"terminal": {"showTerminalProgress": true}}`), or in
pi's settings UI, or under a private `PI_CODING_AGENT_DIR`.

### 4.2 Fullscreen mode: no OSC 133 at all, OSC 9;4 unaffected

```
--- ctlB-fullscreen: alt=1 pb=hidden title=π - proj
    +1s … +11s   pb=indeterminate
    +12s         pb=hidden
    final pb=hidden alt=1 hist=0
    [ctlB-fullscreen] raw=178548B  OSC: {'8;;': 1854, '9;4;3': 12, '0;π - proj': 1, '9;4;0': 1}
```

**Zero OSC 133 in the entire session**, exactly as `TuiAltScreen`'s strip predicts, while OSC 9;4
behaves identically to regular mode. The selection is one line:

```js
// dist/modes/interactive/interactive-mode.js:169-177
export function createInteractiveTui(options) {
    if (options.tuiMode === "fullscreen") return new TuiAltScreen(...);
    return new TuiMainScreen(...);
}
```

and `switchTuiMode()` (line 550) swaps renderers **at runtime**. So OSC 133 from pi is not merely
semantically useless — it is **conditionally absent**, on a switch the human can flip mid-session.

**This also corrects #8's item 4.** #8 recorded `#{alternate_on}` as a per-*harness* property
(`claude`=1, `pi`=0) belonging in the adapter contract. It is not: for `pi` it is
`alt=0, hist=19` in regular mode and `alt=1, hist=0` in fullscreen — a per-*session* property
that a runtime toggle changes. Scrollback-poisoning safety therefore has to be evaluated live,
per pane, not declared once per adapter.

## 5. Reachability, and what `pipe-pane` costs to run continuously

Two tiers, with different version floors and different powers.

| | `#{pane_pb_state}` via `refresh-client -B` | `pipe-pane` raw stream |
|---|---|---|
| tmux floor | **3.7** (released 2026-06-26) | any (3.2, #3's floor) |
| delivery | push, ~1 Hz sampler, 0–1 s lag | continuous bytes |
| sees the 1 Hz keepalive → liveness | **no** (change-only) | **yes** |
| cost per pane | one shared control client | one process + unbounded disk |
| panes per pipe | n/a | **exactly one** — see §5.2 |

Version floors verified against tmux upstream `CHANGES` and by diffing `format.c`/`tty-features.c`
between release tags:

| Capability | Floor | Status |
|---|---|---|
| OSC 9;4 parsed → `#{pane_pb_state}` / `#{pane_pb_progress}` | **3.7** | released 2026-06-26 |
| `progressbar` terminal feature / `Spb` (forwarding outward) | 3.7 | released |
| OSC 133 prompt marking, `next-prompt -o` | 3.4 | released |
| `pane-shell-prompt` / `pane-command-started` / `pane-command-finished` hooks | **3.8** | **unreleased** |
| `pane_last_prompt_time` format | 3.8 | unreleased |
| `refresh-client -B` subscriptions | 3.2 | released — #3 confirmed |

> *"Handle OSC 9;4 progress bar sequence and store in format variables (from Eric Dorland in
> issue 4954)."* — `CHANGES`, `CHANGES FROM 3.6b TO 3.7`

`gh api repos/tmux/tmux/tags` and `/releases` both top out at **3.7c (2026-08-17)**; there is no
3.8 tag. And **`#{pane_last_prompt}` does not exist in any tmux, released or master** — master
has only `pane_last_prompt_time`, a timestamp. Any design wanting prompt *text* from a format has
nothing to build on.

**The consequence for #3's floor.** #3 pinned the substrate at **tmux 3.2**. Reading
`#{pane_pb_state}` needs **3.7**. That is a real cost, and it lands directly on the open
`apbmbp` question: the map records tmux as installed there but its version unconfirmed. The
`pipe-pane` tier is the 3.2-compatible fallback for the same signal, at the cost in §5.1–5.2.

### 5.1 What `pipe-pane` costs

Marginal server cost, same 38 MiB firehose with the pipe off and on, alternating:

```
nopipe1  wall 2.07s  38 MiB  server_cpu 1.67s (43.8 ms/MiB)  sink_cpu 0
pipe1    wall 1.80s  38 MiB  server_cpu 1.35s (35.4 ms/MiB)  sink_cpu 0.22s
nopipe2  wall 1.80s  38 MiB  server_cpu 1.35s (35.4 ms/MiB)  sink_cpu 0
pipe2    wall 2.34s  38 MiB  server_cpu 1.77s (46.4 ms/MiB)  sink_cpu 0.28s
```

**Server-side cost of piping is indistinguishable from zero** — the piped and unpiped runs
bracket each other. Reported as a null result. The cost is entirely in the **sink**: ~6–8 ms CPU
per MiB, plus the write.

The number that decides it is the volume, from the real `pi` capture:

```
pi session : 460789 bytes over 157.5 s          =  2.86 KiB/s mean
  T1-notool: 256208 bytes in 11.5 s             = 21.8 KiB/s while working
  T2-tools : 176704 bytes in  5.4 s             = 31.7 KiB/s while working
  idle     :  27877 bytes over 140.6 s          =  198  B/s
```

A repainting TUI emits every frame, so **~22–32 KiB/s per actively-working pane**. Twenty panes
all working is ~600 KiB/s — **about 2 GB/hour to disk**, for a signal that is two bytes of state.
Idle panes are nearly free (198 B/s). #3 already listed transcript rotation as must-build; this
sizes it. It is not a CPU problem, it is a **disk and retention** problem.

### 5.2 One pipe per pane, and both ways of getting it wrong are silent

```
=== pipe-pane WITHOUT -o, twice ===
after 1st (no -o): pane_pipe=1 pid=2555749
after 2nd (no -o): pane_pipe=1 pid=2555816
marker in first sink : 0        <-- first consumer silently loses the stream
marker in second sink: 2
first pipe process GONE

=== pipe-pane WITH -o, twice ===
after 1st: pane_pipe=1 pid=2543963
after 2nd: pane_pipe=0 pid=           <-- -o TOGGLES: the pipe is now OFF entirely
marker in first sink : 0
marker in second sink: (empty)
first pipe process GONE
```

A pane has **one** pipe. A second `pipe-pane` **replaces** it and kills the first sink; a second
`pipe-pane -o` **turns piping off altogether**. Neither errors, neither warns, and
`#{pane_pipe}` is the only way to notice. So any two components that both want bytes — transcript
capture and byte-level status extraction are the obvious pair — will silently disable each other.
**The pipe is a single owned resource and must be multiplexed by one Jackdaw-owned sink.** This
survives the OSC 133 verdict and belongs in the contract regardless.

## 6. How general is this? (partial)

`cursor` — the other no-channel harness from #2, and the one #8 could not test — is **not
installed on this machine**. It was not tested and no claim is made about it either way. That
gap is now two studies old and needs a machine that has `cursor` on it.

Static scan of the harnesses that *are* installed, for the literal sequences:

```

claude    2.1.231         0     7       14           11
```

- **`claude` 2.1.231: no OSC 133 — but it *does* have OSC 9;4 code.** This is the unfinished

## 7. What this changes for the design

1. **OSC 133 is closed. Do not reopen it.** It is a render artifact with no `D`, byte-adjacent
   `B`/`C`, suppressed on tool turns, and absent entirely in fullscreen mode. #2's conclusion —
   that `pi` has no structured channel — was right about OSC 133.
2. **`pi` has a real structured channel after all: OSC 9;4, surfaced by tmux as
   `#{pane_pb_state}`.** One bit (working / not working) plus a 1 Hz liveness beat, turn-scoped,
   22 ms latency at the emitter, subscribable at 1 Hz. It does not distinguish *blocked* from
   *idle* — but per #2 `pi` has no approval gate, so for `pi` those are the same state.
   This is the first signal that lets `pi` out of #8's "second-class" verdict.
3. **The channel is off by default and must be switched on at launch.** `terminal.showTerminalProgress`
   defaults `false`. An adapter that only *observes* cannot have this signal; one that
   *configures the harness it launches* can. That is #2's launch-arguments requirement, now with
   a concrete instance.
4. **Using it raises the substrate floor from tmux 3.2 to 3.7.** `pipe-pane` is the 3.2-compatible
   fallback for the same bytes, at ~22–32 KiB/s per working pane. Decide deliberately; and settle
   `apbmbp`'s tmux version before it is decided.
5. **The pipe is a single owned resource.** One `pipe-pane` per pane; a second silently steals or
   silently disables. Transcript capture and byte-level extraction must share one sink.
6. **`#{alternate_on}` is per-session, not per-harness.** #8 put it in the adapter contract as a
   declared property. `pi` flips it at runtime with `tuiMode`. It has to be read live, per pane.
7. **The staleness clock is still required**, and for the same reason as #8: tmux holds a stale
   `pb_state` forever if the emitter dies. But this signal fails **stuck-working**, not
   stuck-idle — the safe direction — and the raw stream's 1 Hz keepalive can prove liveness that
   `-B` cannot.

## 8. Where this stops

**Established and finished:**

- The OSC 133 verdict for `pi`, from source and from the wire, with the instrument controlled
  (§1–§4). This closes the ticket's question.
- `pi`'s OSC 9;4 channel: source, semantics, default-off gate, mode-independence, latency,
  abort behaviour, failure direction (§3–§4).
- tmux version floors, verified against upstream `CHANGES` and release tags (§5).
- `pipe-pane` cost and the one-pipe-per-pane constraint (§5.1–§5.2).
- `codex` 0.147.0 emits neither sequence.

**Not finished — do this first:**

1. **Claude Code has OSC 9;4 code and it was never run.** Read from the 2.1.231 bundle:

   ```js
   terminalProgressBarEnabled: Gt().optional()
       .describe("Emit OSC 9;4 progress sequences during long operations")
   ```

   with a settings toggle labelled `"Terminal progress bar"` writing
   `terminalProgressBarEnabled`, and an auto-detect gate:

   ```js
   function c6t(){
     let e = $w()?.progressReporting; if (e !== void 0) return e;
     if (!process.stdout.isTTY) return !1;
     if (Q.WT_SESSION) return !1;
     if (Q.ConEmuANSI || Q.ConEmuPID || Q.ConEmuTask) return !0;
     let t = coerce(Q.TERM_PROGRAM_VERSION); if (!t) return !1;
     if (Q.TERM_PROGRAM === "ghostty")   return gte(t.version, "1.2.0");
     if (Q.TERM_PROGRAM === "iTerm.app") return gte(t.version, "3.6.6");
     return !1;
   }
   ```

   The default path returns `false` under tmux (no `TERM_PROGRAM_VERSION`), which explains #8's
   zero-`9;4` capture — but there is an explicit override (`progressReporting` /
   `terminalProgressBarEnabled`). **If enabling it makes `claude` drive `#{pane_pb_state}` too,
   OSC 9;4 stops being a `pi` curiosity and becomes the cross-harness native status channel the
   whole design has been looking for** — which would change #8's "screen-scraping is the real
   fallback" conclusion substantially. Run it: scratch `CLAUDE_CONFIG_DIR`, setting on, private
   tmux server, same two-observer rig. **Do not restart any live-fleet Claude pane** — 2.1.243
   segfaults on startup fleet-wide.
2. **Whether `pi`'s `agent_end` fires once per turn or once per model round-trip on a *long*
   tool-using turn.** Observed clean on a 5.4 s two-tool turn; a turn with many sequential tool
   calls was not run, and a mid-turn `9;4;0` would be a false-idle — the failure that costs.
3. **`cursor`.** Still untested, still not installed here.
4. **Whether OSC 9;4 survives with a real interactive client attached.** All observations used a
   `-C attach -f no-output` control client only, as in #8.
5. `9;4;2` (error) and `9;4;1;N` (determinate) are unused by `pi`; whether any harness uses them
   is unknown.
